Why move the mocks out of the browser

This repository ships a fully working demo app with no backend behind it. Everything the app talks to — registration, login, users, teams, discussions, comments — is served by Mock Service Worker (MSW), a library that installs a service worker into the page and answers fetch calls before they ever reach the network. The handlers live in src/testing/mocks/handlers/, the data lives in an in-memory @mswjs/data factory in src/testing/mocks/db.ts, and the whole thing is switched on at boot:

// src/main.tsx
enableMocking().then(() => {
  createRoot(root).render(<App />);
});

// src/testing/mocks/index.ts
export const enableMocking = async () => {
  if (env.ENABLE_API_MOCKING) {
    const { worker } = await import('./browser');
    const { initializeDb } = await import('./db');
    initializeDb();
    return worker.start();
  }
};

That design has one very attractive property — clone, yarn dev, and you have a working app — and one awkward consequence: the API does not exist. There is no process listening on a port, no HTTP request crossing a wire, no Set-Cookie header travelling anywhere. The mock DB is a JavaScript object rehydrated from localStorage on every page load, so it belongs to one browser profile in one tab.

That is exactly why docs/testing.md carried this disclaimer: “In the sample app, the tests are ran against the mocked API server, so they are technically not fully e2e.” The Playwright suite drove a real browser, but the browser was talking to itself.

Here is the shape of the old arrangement, and the shape this branch replaces it with. Everything in the first picture lives inside the page:

After the branch, the same handlers run in a separate Node process that the browser reaches over HTTP:

Read the difference off the two figures: the service worker is gone from the page, an express process has appeared beside it, and the store has moved from localStorage — private to one browser profile — to a JSON file on disk that any process can open. What the app does not notice is that it is still the same handler code in both pictures. That is the whole trick, and getting it to be true is most of the work.

The branch gets there in two steps. First it makes the mock API runnable as a standalone HTTP server: a new mock-server.ts entrypoint, plus the surgery on the handler code needed to let it run outside a browser at all — no window, no localStorage, real cookies, real status codes. Then it points the end-to-end suite at that server, so the Playwright tests finally deserve the name.

Teaching the handlers to live outside a browser

Now the interesting part. The handler code was written on the assumption that a browser is present, and that assumption is scattered across three separate places. Each one had to be made isomorphic — able to run in either environment without the caller knowing which.

1. Where the data lives. db.ts grows a Node branch. In the browser nothing changes; in Node, the same data round-trips through a mocked-db.json file (added to .gitignore in this commit), created empty on first read:

+  if (typeof window === 'undefined') {
+    const { readFile, writeFile } = await import('fs/promises');
+    try {
+      const data = await readFile(dbFilePath, 'utf8');

+    } catch (error: any) {
+      if (error?.code === 'ENOENT') {

+        return emptyDB;
+      }
+      console.error('Error loading mocked DB:', error);

+  // If we are running in a browser environment
+  return Object.assign(JSON.parse(window.localStorage.getItem('msw-db') || '{}'));

Note the await import('fs/promises'). A static import of a Node built-in at the top of db.ts would be bundled into the browser build and break it. A dynamic import inside the typeof window === 'undefined' branch is never evaluated in the browser, so the bundler leaves it alone.

Touching disk is asynchronous, and that colour spreads: loadDb, storeDb, persistDb and initializeDb all become async, and every persistDb('user') call across the four handler files picks up an await. enableMocking gains one too.

2. Base64. The auth token is a base64-encoded user object, encoded with window.btoa. In Node there is no window, so utils.ts picks its implementation at call time:

Hydrating before listening

Now the question of what is in the database. Recall that db is an in-memory @mswjs/data factory, and initializeDb() is what replays the persisted records back into it. In the browser that call sits in enableMocking(), which runs before React mounts. The standalone server had no equivalent — it called app.listen straight away, so a request arriving before anything had written to the factory would find it empty even though mocked-db.json was full. The fix is to make hydration a precondition of listening:

-app.listen(env.APP_MOCK_API_PORT, () => {
-  console.log(
-    `Mock API server started at http://localhost:${env.APP_MOCK_API_PORT}`,
-  );
+initializeDb().then(() => {
+  console.log('Mock DB initialized');
+  app.listen(env.APP_MOCK_API_PORT, () => {
+    console.log(
+      `Mock API server started at http://localhost:${env.APP_MOCK_API_PORT}`,
+    );
+  });
 });

This is what makes the Playwright setup project work. auth.setup.ts registers a user through the UI and saves the resulting cookie to e2e/.auth/user.json; the chromium project then loads that storageState into every spec. The cookie is only useful if the server still knows the user it names — and the server's memory of that user is exactly the row persistDb('user') wrote into mocked-db.json.

Three smaller changes fall out of running it for real. The CORS origin is widened from the configured app URL to a wildcard, with the reason written into the code — // allow the app on whichever port vite picked. vite.config.ts gains a preview: { port: 3000 } block so a preview server lands on the same port the dev server uses, keeping VITE_APP_URL honest either way. And storeDb loses the key parameter it never used — the Node branch writes a fixed path and the browser branch writes a fixed localStorage key, so the argument had no reader:

Where that leaves things

Put the two commits together and the story is a single move with a long tail. The move: take the array of MSW handlers that used to be mounted into a service worker, and mount it into an Express app instead. The tail is everything that was implicitly relying on “there is a browser here and there is no network here” — localStorage, window.btoa, reading cookies out of document, throwing instead of returning a status code, and a client that never had to think about origins or credentials.

What the repository gains is a mock backend that behaves like a backend. It listens on a port, it logs requests through pino-http, it answers 401 when you are not logged in, it sets cookies that a browser stores and returns, and its data outlives the tab because it is a file. Several processes can now share one database — which is what turns the Playwright suite from a browser talking to itself into two processes talking over HTTP.

A few properties are worth carrying away, because they are consequences of the design rather than oversights:

  • mocked-db.json persists between runs. Nothing truncates it; loadDb only creates it when it is missing. Each e2e run registers a fresh user via auth.setup.ts and adds to the file, which is why CI uploads it as a build artifact.
  • resetDb is still browser-only. It calls window.localStorage.clear() and has no Node branch, unlike its neighbours in db.ts.
  • In-browser mocking has not gone away. .env.example still ships VITE_APP_ENABLE_API_MOCKING=true, so a plain yarn dev clone-and-run keeps working exactly as before. The standalone server is the second mode, selected by .env.example-e2e, not a replacement for the first.
  • The handler code is now the shared contract between both modes. Anything added to src/testing/mocks/handlers/ has to stay isomorphic — no bare window, and a persistDb call that is awaited — or it will work in one mode and fail in the other.
